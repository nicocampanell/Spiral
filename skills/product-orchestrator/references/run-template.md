# Run record

Copy only for a substantial run. The lead alone edits this file; workers return their own results. Use a unique run directory and relative evidence paths. Keep credentials and private payloads out of logs.

## Contract

- Goal and intended user:
- Canonical project Notion home and child-document URLs/IDs, with verified context:
- the project owner's confirmed vision and chosen direction; proposals/assumptions kept separate:
- Scope and explicit exclusions:
- Constraints and significant assumptions:
- Acceptance criteria with stable IDs, criteria revision, and required checks:
- User-approved limits; otherwise three repair rounds per failed work unit:
- Working milestone for the project owner to review; first-build bar is a polished coherent core flow:
- Baseline revision plus working-change identity and existing check outcomes:

## Work graph

| Task ID | Role / actual agent ID | Owned paths | Inputs/dependencies | Deliverable/check / criteria revision | Status | Repair rounds |
|---|---|---|---|---|---|---|

Record shared interface decisions and file handoffs here. Task statuses: queued, running, awaiting-input, ready-for-verification, failed, verified, blocked, cancelled. An implementer's “done” becomes ready-for-verification.

## Decisions and blockers

Record the decision, reason, owner, and what unblocks any pending issue. Distinguish user constraints from the lead's assumptions.

For substantial backend work, link the existing architecture decision or record the stack, source paths, changed data flow and tradeoffs here. For system mapping, design review, the first vertical slice and readiness, record status, reviewer, evidence and which work is blocked.

## Verification history

Append criterion ID, criteria revision, artifact identity, verifier, actual check, observed result, evidence path, verdict, and repair owner. Mark stale evidence explicitly after relevant artifact or criteria edits. Keep failed attempts visible.
